# apply-layer-convention

ここにあるのは言語に依らない一般則で、各言語の規約はそれを自分の言語の形へ写すだけにする。資料に無いことは推測で補わない（`develop-inside-out` の規律）。集約と状態の切り方、並行実行で要る保証、分離レベルとやり直し、技術的な処理のライフサイクルは資料を作る側が決め、ここではそれを写す位置だけを決める。

## パターンは業務知識の複雑さで選ぶ

拒否があるかどうかでは選ばない。拒否はどんな処理にもあり、それだけで集約を作ると、状態を持たない処理に空の型が並ぶからである。問いは二つで、どちらかに当たれば戦術的 DDD で書く。状態によって受ける操作が変わるか。複数の値や事実にまたがる不変条件を、自分の状態と受け取った材料から判断するか。

どちらにも当たらない処理は単純なパターン（トランザクションスクリプト）で書き、usecase の手順が DB へのアクセスを受け持つ口（リポジトリ相当）を順に呼ぶ。要求、回収、完了の段階を持っていても、それが業務の状態ではなく技術的な処理のライフサイクルなら単純なパターンである。どちらのパターンでも、値は値オブジェクトで組み立て、DB へのアクセスはリポジトリ相当の口に置き、手順とトランザクションの境界は usecase が持つ。技術的な処理の途中で業務の判断が要るなら、発生元の集約のコマンドで確定させて要求に載せて運び、手順が分岐してよいのは処理の段階、要求が運んだ閉じた値、エラーの処理の表だけにする。

## 責務は一つの持ち主に置き、依存は外から内へ向ける

持ち主は、ドメイン、集約のリポジトリ、command の usecase、単純なパターンの手順とその口、query の usecase と読み取りの口、Query の実装、入口（RPC の handler、メッセージの受信、ワーカーの巡回）のどれか一つである。依存は入口から usecase、usecase からドメインとポートへ向き、実装はポートを満たす。ドメインは永続化、転送の形式、時計、採番を知らない。「共通」「サービス」のような持ち主を決めない置き場へ逃がさない。

書き込みは集約を復元して操作し、リポジトリから保存する。一覧、件数、検索、存在確認は、query の usecase が所有する読み取りの口と平らな読み取りモデルに置き、Query の実装が集約を復元せずに満たす。一覧をリポジトリへ置く、Query で集約を復元する、という指定は置き換えずに `query_role_conflict` として止まる。

## command は、見つける、一回呼ぶ、適用するだけにする

command の usecase は、リポジトリの Find で集約（生成なら初期状態の集約）を得て、コマンドを一回呼び、結果のイベントを Apply で保存する。判断の材料（ほかの集約から集めた事実）は Find が読んで初期状態の集約へ持たせ、Find は判断しない。usecase は読み取りの口を呼ばず、状態を見て分岐しない。材料を usecase が集めると、集めるための分岐が usecase に入り、材料と保存が同じトランザクションで読まれる保証も崩れるからである。受けない状態の拒む理由が資料に無ければ、その command は書かずに資料へ返す。

外から来たプリミティブは、入口で値オブジェクトへ一度だけ変換する。業務の時刻は入口が時計から一度だけ取り、巡回なら一回の巡回の始めに取って全件に同じ値を渡す。業務が時刻を決めない出来事の時刻は、リポジトリが記録のときに取る。応答に返す識別子は usecase がトランザクションの外で採番してコマンドへ渡す。やり直しても同じ識別子を使うためである。

## 不変条件は三つの置き場に分け、トランザクションは usecase が張る

構造の条件（一つの値が有効である条件）は値オブジェクトの生成が、事前条件（操作の時点の状態と材料で決まる条件）は集約のコマンドが、集合の条件（一意、参照、同時の書き込みにまたがる条件）は DB の宣言的な制約が守り、リポジトリが違反を業務の拒否へ翻訳する。制約を宣言できないなら、ロックなどの代わりを発明せずに止まる。トランザクションは usecase が張り、リポジトリと口は渡されたトランザクションの上で動く。分離レベルとやり直しは物理設計の資料が操作ごとに決めたものを渡し、指定が無ければ物理設計の資料へ返す。

## 後続の処理は Outbox で分ける

一つの command が書く集約は一つを基本にする。通知の送信やタイムラインの更新のように、同期で行うと外部の遅延や失敗が業務の変更まで止める処理は、Outbox で非同期にする。発生元の変更と要求の記録を同じトランザクションで保存し、単純なパターンの手順が別のトランザクションで要求を回収して処理する。外部との通信はトランザクションの外に置き、処理を冪等にし、進捗を一件ごとに確定させる。資料が二つの集約を同じ時点で成立させると定めたときだけ、一つのトランザクションで二つを書く横断の command を置き、先の結果を値として次のコマンドへ渡す。同じ時点か別の時点かが資料に無ければ問う。

## 失敗の影響は、全体に及ぶかどうかの一つの基準で閉じ込める

複数の件を順に処理するとき、一件に閉じた失敗（業務の規則に反する、同時更新で競合した、その行の破損）は記録して次へ進み、全体に及ぶ失敗（依存先が利用できない、時間切れ）は残りを試さずに打ち切る。どの分類がどちらかは各言語のエラーの規約の表が持つ。利用者へ返す一覧では壊れた一件だけを除いて記録し、作業待ちの行は黙って除かない。巡回の相手が command なら巡回が候補を選んで一件ずつ呼び、ループと閉じ込めを持つ。相手が手順ならループと閉じ込めは手順が持ち、巡回は一度呼ぶだけにする。両方に書くと記録が二重になる。

## 止まるとき

責務を識別できないか、どの持ち主にも当たらないとき、`query_role_conflict` のとき、集合の条件を DB で宣言できないとき、パターン、集約の境界、後続の処理の時点、物理設計の指定が資料から一つに決まらないときは、決まらない点と提案を返して止まる。実装の変更を頼まれたときだけコードを直し、依存の検査、ビルド、テストを通す。

## 例

図書館の貸出は状態で受ける操作が変わるので戦術的 DDD になり、本を借りる command では Find が利用者の貸出状況を初期状態の貸出へ持たせ、コマンドが上限と延滞を判断する。延滞の通知の回収と発行は技術的な処理のライフサイクルなので単純なパターンになる。反例は、延滞にする usecase の中で候補の一覧を読み、件数を見て分岐する形である。同じ本を二人が同時に借りる場面はコマンドでは拒めないので、部分一意の制約が守る。
