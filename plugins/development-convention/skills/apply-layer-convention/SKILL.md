# apply-layer-convention

[工程順序の定義](playbook.yml)を最初に読み、同じ agent が `steps` を宣言順に実行する。YAML は工程の順序だけを決め、各工程の判断はこの本文と参照資料を読んで行う。失敗した工程は成功扱いせずに止まり、完了した工程、根拠、未決を残す。再開するときは、最初の未完了の工程から続ける。

この skill は、処理ごとに実装パターンを選び、責務の持ち主と整合性の守り方を、言語に依らずに決めて、コードへ当てる。言語ごとの package、directory、import path は決めない。それは各言語の規約が、ここで決めた論理の責務を入力として決める。機能要求の発見、業務規則の補完、実装の順序、不要な公開面の選別、DB 製品や非同期基盤の選定も行わない。

## 入力

対象の repository と、判断または変更するコードの範囲を絶対 path で受け取る。対象の業務操作、読み取り、整合性の規則を受け取る。根拠として、業務知識、ドメインモデル、論理データモデル、物理設計の資料と、その版または観測時点を受け取る。実装の変更まで依頼されているか、論理の判断だけかも受け取る。

`references` として、追加で従う資料の絶対 path の配列を受け取ることがある。受け取ったら手順の最初に読み、この規約と併せて従う。プロジェクト固有の規約（置き場、命名）は、対象 repository の AGENTS.md と CLAUDE.md と `references` で渡される。この skill は既定値を持たない。

文書の ID は、その文書の中でだけ有効である。異なる文書を同じ番号で結ばず、資料の所在と版、業務操作、期待状態の組で対応を追う。

## 判断の持ち主

この skill が持つのは、言語に依らない論理の判断である。実装パターンの選択、command の流れ、入力の変換の位置、時刻と採番の持ち主、トランザクションの所有、Outbox、失敗の影響を閉じ込める基準がそれにあたる。判断の根拠と例は [責務と整合性の判断](references/layer-and-consistency.md) にある。

資料からずらさない規律と、資料が曖昧なら止まって提案する規律は `develop-inside-out` が持つ。この skill も同じ規律に従い、資料に無いことを推測で補わない。集約と状態の切り方、並行実行で必要な保証、分離レベルとやり直し、技術的な処理のライフサイクルは、資料を作る側が決める。この skill は、それを写す位置を決めるだけである。

## 作業手順

### 1. 実装パターンを選ぶ

`references` があれば、この工程の最初に読む。

処理ごとに、その処理が持つ業務知識の複雑さでパターンを選ぶ。拒否があるかどうかでは選ばない。拒否はどんな処理にもあるからである。問いは二つで、どちらかに当たれば戦術的 DDD で書く。一つ目は、状態によって受ける操作が変わるかである。資料の状態遷移図に複数の状態があり、コマンドごとに受ける状態が決まっているなら当たる。二つ目は、複数の値や事実にまたがる不変条件を、自分の状態と受け取った材料から判断するかである。

どちらにも当たらない処理は、単純なパターン（トランザクションスクリプト）で書く。usecase の手順が、DB へのアクセスを受け持つ関数の集まり（リポジトリに相当するもので、以下「口」と呼ぶ）を順に呼び、集約や状態ごとの型は作らない。単純なパターンに入る拒否は、値の形の検証、DB の制約で守れる拒否、存在しないことによる拒否の三種類である。要求、回収、完了という段階を持つ処理でも、それが業務の状態ではなく技術的な処理のライフサイクルなら、単純なパターンである。

選んだパターンと、二つの問いへの答えと、根拠にした資料の箇所を判断記録に残す。業務知識が状態を持たないと書いていれば、一つ目の問いには当たらない。止まるのは、業務知識もドメインモデルも状態について何も書いておらず、どちらとも決められないときだけで、そのときは推測で選ばずに資料の持ち主へ問う。ドメインモデルの種別（集約ルートとして描かれているか）では選ばない。業務の決まりが薄い概念も、集約ルートとして描かれるからである。

### 2. 責務の持ち主と依存の向きを決める

各責務を、ドメイン、集約のリポジトリ、command の usecase、単純なパターンの手順、手順が所有する口、query の usecase、入口、Query の実装のどれか一つに分ける。入口は、RPC の handler、メッセージの受信、ワーカーの巡回のように、外からの要求を受けて usecase を呼ぶところである。分けた責務ごとに、所有する型、許す依存、禁じる依存を記録する。「共通」「サービス」「ヘルパー」のように持ち主を決めない置き場へ逃がさない。どれにも当たらない責務は、分割の案と影響の範囲を返して止まる。

書き込みは集約を復元して操作し、リポジトリから保存する。読み取りは、query の usecase が所有する読み取りの口と平らな読み取りモデルを使い、Query の実装から得る。一覧、件数、検索、存在確認をリポジトリへ置かない。Query の実装は集約を復元しない。これを破る指定があれば、別の責務へ自動で置き換えず、`query_role_conflict` として返して止まる。

### 3. command の流れと、入力、時刻、採番の持ち主を置く

戦術的 DDD の command の usecase は、集約を見つける、コマンドを一回呼ぶ、結果を適用する、の三つだけにする。判断の材料（ほかの集約から集めた事実）は、リポジトリの Find が読んで生成前の集約へ持たせる。usecase は読み取りの口を呼ばず、状態を見て分岐しない。受けるか拒むかは、その状態の集約のコマンドが決める。

外から来たプリミティブは、入口で値オブジェクトへ一度だけ変換する。usecase とドメインは検証済みの値だけを受け取る。業務の時刻は、入口が時計から一度だけ取ってコマンドへ渡す。記録だけの時刻（出来事の時点を業務が決めないもの）は、リポジトリが記録のときに取る。応答に返す識別子は、usecase が採番してコマンドへ渡し、採番はトランザクションの外で行う。ドメインは時計も採番も持たない。

### 4. 不変条件とトランザクションを置く

構造の条件は値オブジェクトの生成が守る。事前条件は、Find が集めた材料を使って集約のコマンドが判断する。集合の条件（一意、参照、同時の書き込みにまたがる条件）は DB の宣言的な制約が守り、リポジトリが違反を業務の拒否へ翻訳する。選んだ DB で制約を宣言できないなら、ロックなどの代わりを発明せずに止まる。

トランザクションは usecase が張る。分離レベルと、トランザクションの中でのやり直しの回数は、物理設計の資料が操作ごとに決めたものを渡す。既定の分離レベルに頼らない。物理設計に指定が無ければ、推測で補わずに物理設計の資料へ返す。

一つの command が書く集約は一つを基本にする。メールや通知の送信のように、同期で行うと外部の遅延や失敗が業務の変更まで止める処理は、Outbox で非同期にする。発生元の変更と要求の記録を同じトランザクションで保存し、単純なパターンの手順が別のトランザクションで要求を回収して処理する。資料が二つの集約を同じ時点で成立させると定めたときだけ、二つを一つのトランザクションで書く横断の command を置く。同じ時点か別の時点かが資料に書かれていなければ、推測せずに資料の持ち主へ問う。

外部との通信を挟む手順では、外部への通信をトランザクションの外に置き、処理を冪等にし、進捗を一件ごとのトランザクションで確定させる。

### 5. 失敗の影響を閉じ込める範囲を決める

複数の件を順に処理する場面（巡回、一件ずつの発行、一覧）で、一件の失敗が関係のない範囲まで止めないようにする。基準は、その失敗が全体に及ぶかどうかの一つだけである。一件に閉じた失敗（業務の規則に反する、同時更新で競合した、その行の破損）は、記録して次の一件へ進む。全体に及ぶ失敗（依存先が利用できない、時間切れ）は、残りを試さずに打ち切って返す。分類ごとにどちらになるかは、各言語のエラーの規約の表が持つ。

利用者へ返す一覧では、壊れた一件だけを除いて記録し、残りを返す。作業待ちの行（Outbox の要求）は黙って除かず、技術的な処理のライフサイクルが定める終わり方で記録する。巡回の相手が command なら、巡回（入口）が候補を選んで一件ずつ command を呼び、ループと閉じ込めを持つ。相手が単純なパターンの手順なら、ループと閉じ込めは手順が持ち、巡回は手順を一度呼ぶだけにする。

### 6. 適用して依存を検査する

実装の変更を依頼されているときだけ、対象のコードを直す。判断だけの依頼では変えずに、責務の対応を返す。どちらの場合も、対象の言語で使える依存の検査、ビルド、対象のテストを実行する。言語ごとの配置は、入力された言語の規約がある場合だけ検査し、この skill から補わない。検査が失敗した状態を完成として扱わない。

## 出力

責務ごとの論理の持ち主、選んだパターンと根拠、依存の向き、不変条件の権威、トランザクションの境界と物理設計の指定、Outbox の有無、失敗を閉じ込める範囲を判断記録として返す。実装の変更を依頼された場合は、それを反映したコードと対象のテストも返す。実行した検査とその結果、資料の所在と版から業務操作と期待状態への追跡も返す。

## 停止条件

次のときは止まる。止めた判断、必要な入力または確認、根拠の資料、影響の範囲を返し、確定した判断は捨てない。

対象の範囲か、判断する責務を一つも識別できないとき。責務がどの持ち主にも当たらないとき。一覧や件数をドメインやリポジトリに置く指定か、Query で集約を復元する指定があるとき（`query_role_conflict`）。選んだ DB で集合の条件を宣言できないとき。資料が曖昧で、パターン、集約の境界、後続の処理の時点、物理設計の指定のどれかが一つに決まらないとき。このときは推測で埋めず、問題と提案を資料の持ち主へ返す。実装の変更に必要な権限か検証の手段が無いとき。依存の検査、ビルド、対象のテストが失敗したとき。

## 完了条件

対象の処理ごとにパターンが選ばれ、その根拠が資料へ追える。各責務が一つの持ち主を持ち、依存の向きが外から内である。command の usecase は読み取りの口を呼ばず、状態で分岐しない。入力の変換は入口にあり、業務の時刻は入口から、採番は usecase から渡る。不変条件とトランザクションの境界が資料どおりで、分離レベルは物理設計の指定を渡している。失敗を閉じ込める範囲が一つの基準で決まっている。言語ごとの物理配置を出力していない。

## 使用例

典型例：図書館の貸出は、貸出中、延滞、返却済みで受ける操作が変わり、貸出状況から借りられるかを判断するので、戦術的 DDD になる。本を借りる command は、Find が利用者の貸出状況を読んで生成前の貸出へ持たせ、コマンドが上限と延滞を判断する。

似て非なる例：延滞の通知の回収と発行は、要求、回収、完了の段階を持つが、それは技術的な処理のライフサイクルなので、単純なパターンになる。延滞にする command が、同じトランザクションで通知の要求を Outbox に記録する。

反例：延滞の候補を選ぶ読み取りを、延滞にする command の usecase の中で呼び、件数を見て分岐する。usecase が判断を持つことになるので、候補の選択は巡回が query で行い、command は一件だけを扱う。

境界例：蔵書の登録は、同じ ISBN の重複を一意制約で、存在しない本の更新を存在の確認で拒むだけなので、単純なパターンになる。重複の拒否は、名前付きの制約の違反をリポジトリ相当の口が業務の拒否へ翻訳する。
