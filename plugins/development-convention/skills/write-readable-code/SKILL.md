# write-readable-code

コードを読む人が、業務の資料とコードを突き合わせ、コードだけから業務の判断を追えるようにする。そのための三つの規律をここにだけ置き、各言語の規約はその言語での形だけを持つ。

## 名前は業務の言葉で付ける

型、関数、メソッド、モジュールの名前は、業務の資料（業務知識、ドメインモデル、データモデル）にある言葉で付ける。データや処理の形から付けた名前（二つを束ねた「組」、何かを「管理する者」、「データ」「情報」「記録」、何かを「処理する者」「探す者」）は、その型が業務の何を表すかを教えず、同じ形をした別の概念とも見分けられない。業務の言葉の名前なら、読み手は資料のどこを読めばよいかが分かる。

名前を付けるときは、二つの問いを順に当てる。一つ目は、その語が業務の資料にあるかで、あればその語を使う。業務の語があるのに、生成、開始、削除のような処理の一般語へ置き換えない。二つ目は、無いなら、それが業務に対応する概念を持たない技術の部品（トランザクション、interceptor、Outbox、時計、採番器、変換）かで、そうなら技術の語で名付ける。業務の概念なのに資料に語が無いなら、それは名前の問題ではなく資料の不足なので、推測で名付けずに止まり、業務の言葉と名前の候補を資料への提案として返す。

英名は、業務知識の資料のユビキタス言語が業務の言葉ごとに一つ決めたものを、そのまま使う。業務イベントは、成立した業務操作を過去形で表す。資料に英名が無ければ自分で英訳せずに止まり、候補を提案する。同じ概念に二つの英名が生まれると、資料とコードを突き合わせられなくなるからである。

## コメントは、自分の責務だけを業務の言葉で書く

コメントには、コードから分からないことだけを書く。業務上の意味、似た概念との違い、不変条件、呼び出し順やトランザクションの境界のようにシグネチャから読めない契約がこれに当たる。識別子を言い換えただけのコメントと、本文を上から説明する実況は書かない。公開されていることだけを理由にコメントを付けない。

その型や関数自身の目的と責務だけを書き、何を担い何を担わないかを自分の言葉で閉じる。使う側の都合（「〜の usecase のポートを満たす」「〜が組み立てで注入する」）、別の場所の型やモジュールの名前、担わないものを誰が担うかは書かない。使う側が動いたときに陳腐化するからである。値やエラーには、それが業務上どの条件に反するのか、どの業務の概念なのかを業務の言葉で書き、「資料に無い」「言語の都合」「実装の都合」のように存在の理由を実装の事情に帰する断り書きは書かない。

外部の値（外部サービスの URL、環境変数、プロトコルの手続き名、鍵の識別子）には、実際に来る値のサンプルを一つ添える。説明を長くするより、サンプル一つのほうが伝わる。テストとテストデータの組み立てのコメントも同じ基準で、既定値がどの BDD の登場人物や状態を表すか、なぜ行を直接入れる必要があるかは書き、表の変数名や期待値や手順の言い換えは書かない。コメントを書く言語は、対象の repository の規約に従う。

## テストのために実装を曲げない

テストは、本番と同じ公開の振る舞いを観測する。テストのためだけに、公開の関数や getter、フラグ、分岐、差し替えの口を実装へ足さない。内部をテストへ晒す仕組みも使わない。内部の状態を見たくなったら、それは型に業務の問い合わせが足りないか、テストを置く層が違うという合図で、公開の振る舞いで観測できる形へ言い直す。言い直せない内部の関数は、それ自身が一つの責務として公開されるべきかを考える。

どの境界なら差し替えの口を置いてよいかは、testing-strategy の `design-test-strategy` の test-strategy-judgment.md に従う。公開シンボルの要否そのものは、`apply-yagni` の基準で決める。

## 止まるとき

業務の概念の名前か英名が資料に無いときは、推測で名付けずに止まって資料へ提案する。技術の部品の名前や分割の揺れでは止まらず、最も筋の良い形を採って報告に示す。テストのために実装を変えないと観測できないと判断したら、実装を曲げずに、足りない問い合わせかテストの層の見直しを提案する。

## 例

貸出の「貸出状況」を `LoanStatusInfo` や `UserLoanData` と名付けるのはデータの形からの名前で、資料の語の英名 `Standing` を使う。資料に「延滞の通知の要求」の英名が無いなら、`NoticeRequestRecord` と作らずに英名の候補を資料へ提案する。「貸出のリポジトリの実装。LoanUsecase から呼ばれる」というコメントは使う側の都合なので、「貸出と、その出来事を記録する」と自分の責務だけを書く。テストで貸出の内部の版を見たいから `Version()` を公開する、というのは実装を曲げることで、版の衝突は保存したときの競合として公開の振る舞いで確かめる。
