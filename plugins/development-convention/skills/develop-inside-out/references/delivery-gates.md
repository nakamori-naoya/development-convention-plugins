# 内側から外側へ進むゲート

# 受け入れの起点

一つのユーザージャーニーの場面を、一つの受け入れテストへ写す。開始の状態が Given、利用者の行為が When、外から観測できる完了の状態が Then にあたる。受け入れテストは外部との境界を入口にし、実 DB まで通す。

最初の赤は、対象の機能がまだ無いことの証明である。何を赤とみなし、何を赤の証拠にしないかは、この入口の SKILL.md の「赤とは何か」に従う。

# ゲートの順序

```text
一つの場面を受け入れテストへ写す（赤）
  ↓
業務規則をドメインのテストで通す
  ↓
command：Before と After を実 DB のリポジトリのテストで通す
query：読み取りの口の実装を実 DB のテストで通す
  ↓
成功、取り消し、Outbox の同じトランザクションを usecase のテストで通す
  ↓
入口の変換を実装し、受け入れテストを緑にする
```

矢印の下へ進めるのは、当てはまる上のゲートがすべて緑のときだけである。読み取りだけの場面と単純なパターンの処理では、ドメインのゲートを非該当として記録する。永続化しない計算では、リポジトリのゲートを非該当として記録する。非該当と失敗を取り違えない。

# テストの持ち場

ドメインのテストは業務規則を網羅する。受ける場合、拒む場合、境界、発する出来事を確かめ、DB も外部との境界も使わない。

リポジトリのテストは、資料の Before と After を実 DB で確かめる。After に挙がったテーブルは全行と全列で突き合わせ、挙がっていないテーブルは行数が変わらないことを確かめる。集合の条件は DB の制約で守られ、違反が業務の拒否へ翻訳されることを確かめる。

Query の実装のテストは実 DB を使い、読み取りの口の戻り値が平らな読み取りモデルで、集約を復元していないことを確かめる。

usecase のテストは、成功の一本、途中で失敗したときに書き込みが残らないこと、Outbox を使うなら発生元の変更と要求の記録が同じトランザクションに残ることを確かめる。業務規則を網羅し直さない。

受け入れテストは、利用者の目的が外部との境界から達成できることを確かめる。業務規則の全部の場面を走らせ直さない。

# 資料が決めないときは止まる

ゲートを進める途中で、資料が曖昧、資料どうしが食い違う、期待状態が一つに決まらない、のどれかに出会ったら、推測で埋めずに止まる。止まるときは、何が決まらないか、どのテストの期待状態が変わるか、資料をどう直せば決まるかの提案を、資料を作る側へ返す。実装の側で資料を書き換えない。機械の検査を通すためだけに資料を書き換えることもしない。

# 追跡

資料の ID は、資料をまたいで共有しない。資料の絶対 path、版または観測時点、業務操作、操作の前後の期待状態、対応するテストの絶対 path とテスト名の組で、対応を記録する。同じ番号でも、資料、操作、期待状態が違えば別の項目である。

# 例

典型例：本を借りる場面の受け入れテストを赤にし、上限と延滞の拒否をドメインのテストで、貸出中の本の重複を DB の制約とリポジトリのテストで、取り消しを usecase のテストで通してから、入口を実装して緑にする。

似て非なる例：貸出の一覧は業務の状態を変えない。集約とドメインのテストを作らず、Query の実装の実 DB のテストから始める。

反例：受け入れテストの赤の理由が DB の接続設定の欠落なのに、開始の条件を満たしたとみなす。失敗の原因が違うので止まる。

境界例：ドメインモデルに通知の例があっても、論理データモデルが通知の保存を対象外としているなら、通知の保存を含む場面は実装する前に止まる。対象外の指定が外れた版が入力されたときにだけ含める。
