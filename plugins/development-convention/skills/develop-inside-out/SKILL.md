# develop-inside-out

一つのユーザージャーニーの場面を、外部との境界から実 DB まで通す受け入れテストが緑になるまで、内側から外側へ実装する。どの層に何を置くかは `apply-layer-convention` が決め、各層を各言語でどう書き、何をテストするかは各言語の規約が持つ。ここが持つのは、進め方と、資料と赤についての規律である。

## 資料からずらさず、推測で埋めない

実装は資料を写す。資料と実装が食い違ったら、実装の側で資料を書き換えず、資料を作る側への変更の提案として返す。機械の検査を通すためだけに資料を書き換えることもしない。

資料に無い操作や拒否が要ると感じたとき、資料が曖昧なとき、資料どうしが食い違うとき、期待状態が一つに決まらないときは、推測で埋めずに止まり、何が決まらないか、どの期待状態が変わるか、どう決めればよいかを返す。表示の文言や境界の値の丸めのような細部でも同じである。当て推量で書いた実装は、積み重なるほど誰にも説明できなくなるからである。

## 赤とは何か

赤は、テストが、確かめたい対象がまだ無いこと、または対象が期待と違う結果を返すことを理由に失敗している状態である。この定義はここにだけ置き、各層のテスト、言語ごとの規約、不具合の再現テストはここに従う。

まだ無い型や関数を呼んでいてビルドが失敗するのも赤である。そのビルドの失敗は、対象がまだ無いことをそのまま示している。赤にするためだけに空の実装を先に置く必要はない。

失敗の理由が対象の外にあるときは赤ではない。接続の失敗、設定の不足、DB やコンテナのような実行環境が無いこと、無関係なテストの故障、下の層の赤、テストの書き損じ（まだ無い対象の名前と関係のない構文や import の誤り）がこれに当たる。環境かテストを直すか、実行できないとして止まる。赤を確かめたら、理由を「対象がまだ無い」か「結果が期待と一致しない」に分けて記録する。最初から緑なら、対象が既にあるのか、テストが何も観測していないのかを確かめるまで実装へ進まない。

## 一つの単位は、テスト、赤、実装、緑、整えるの順で進める

一つの単位は、一つの層の一つの対象である。赤を確かめてから実装する。実装の間はテストを変えず、テストの誤りに気付いたら実装を止めてテストへ戻り、赤からやり直す。緑は、対象のテストだけでなく、同じ package の全テストとその言語の機械検査が通った状態である。整えるときは、前後で同じテストが緑で、ケースの識別と期待を変えない。その層が主に担わない観点を、その単位のテストに足さない。

## 層は内側から外へ、下のゲートが緑のときだけ進む

1. 場面を一つの受け入れテストへ写す。開始の状態が Given、利用者の行為が When、外から観測できる完了の状態が Then で、入口から実 DB まで通す。対象の機能がまだ無いことが理由で赤になることを確かめる。
2. ドメイン。場面が業務の状態の変更か業務の判断を含むときに、業務知識の拒む理由とドメインモデルの状態とコマンドを写す。業務規則の網羅はこの層で行う。
3. 永続化または読み取り。command なら論理データモデルの Before と After を実 DB で、query なら読み取りモデルを実 DB で確かめる。
4. usecase。呼ぶ集約とリポジトリか読み取りの口のテストがすべて緑のときに行う。
5. 入口。usecase のテストがすべて緑のときに実装し、最初の受け入れテストを緑にする。受け入れテストだけを通す分岐や固定の値を足さない。緑にならなければ、最初に失敗した層へ戻る。

読み取りだけの場面と単純なパターンの処理ではドメインの層を、永続化しない計算では永続化の層を、非該当として理由とともに記録する。非該当と失敗を取り違えない。

資料の ID は資料の中でだけ有効なので、追跡は資料の絶対パスと版、業務操作、期待状態、対応するテストの組で記録する。

## 止まるとき

対象の場面が無いとき、資料が曖昧か食い違い業務操作や期待状態、永続化の範囲、command か query かが一つに決まらないとき、論理データモデルが対象外とした永続化を場面が必要とするとき、下の層が赤のとき、集合の条件を DB で宣言できないか物理設計に必要な指定が無いとき、実 DB の検査を実行できないときは、次の層へ進まずに止まる。止めたゲート、最初の失敗、必要な確認、変更したファイル、手を付けていない層を返す。

完了したら、受け入れテストと各層のテストの結果、資料からテストへの追跡、実行しなかった検査を返す。

## 例

「利用者が本を借りる」場面を受け入れテストにし、貸出の集約のテスト、貸出と出来事の Before と After の実 DB のテスト、usecase のテストの順に緑にし、最後に RPC の入口で受け入れを緑にする。貸出の一覧を表示する場面は読み取りだけなので、ドメインを非該当にして Query の実装のテストから始める。反例は、資料の「貸出日の14日後」の起点が曖昧なのに「翌日から数えて14日」と推測して実装することで、止まって資料の持ち主へ問う。受け入れテストの赤の理由が DB の接続設定の欠落なら、赤ではないので止まる。
