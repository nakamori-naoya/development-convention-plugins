# develop-inside-out

[工程順序の定義](playbook.yml)を最初に読み、同じ agent が `steps` を宣言順に実行する。YAML は工程の順序だけを決め、各工程の判断はこの本文と参照資料を読んで行う。失敗した工程は成功扱いせずに止まり、完了した工程、根拠、未決を残す。再開するときは、最初の未完了の工程から続ける。

一つのユーザージャーニーの場面と、それを成立させる確定済みの資料を受け取り、外部との境界を実 DB まで通す受け入れテストが緑になるまで、内側から外側へ一つの機能を実装する。資料をテストへ写し、各層を下の層の合格の後にだけ実装する。場面や業務規則の発見、層の決め方そのもの、資料に無い受け入れ条件の追加、複数の機能の一括実装は行わない。

## 入力

対象の repository と実装の対象、テストとビルドの方法を受け取る。根拠として、ユーザージャーニーの一つの場面（開始の状態、利用者の行為、観測できる完了の状態）、関係する業務知識、ドメインモデル、論理データモデル、物理設計の資料を、版または観測時点とともに受け取る。既存のコードとテストも受け取る。

`references` として、追加で従う資料の絶対 path の配列を受け取ることがある。受け取ったら手順の最初に読み、この規約と併せて従う。プロジェクト固有の規約は、対象 repository の AGENTS.md と CLAUDE.md と `references` で渡される。この入口は既定値を持たない。

資料の ID は、その資料の中でだけ有効である。追跡は、資料の絶対 path と版、業務操作、期待状態の組で記録し、別の資料の同じ番号を同じ事項とみなさない。

## 資料からずらさず、推測で埋めない

実装は資料を写す。資料と実装が食い違ったら、実装の側で資料を書き換えず、資料を作る側への変更の提案として返す。機械の検査を通すためだけに資料を書き換えることもしない。

資料に無い操作や業務の拒否が要ると感じたら、実装で補わずに資料へ返す。資料が曖昧なとき、資料どうしが食い違うとき、期待状態が一つに決まらないときは、推測で埋めずに止まり、何が決まらないか、どの期待状態が変わるか、どう決めればよいかの提案を返す。表示の文言や境界の値の丸めのような細部でも、資料に無ければ同じように止まって問う。当て推量で書いた実装は、積み重なるほど誰にも説明できなくなるからである。

どの層に何を置くか、実装パターンと責務の持ち主は `apply-layer-convention` が決める。この入口は、その判断に従って層を順に進める。各言語での一つの層の書き方は、その言語の規約が持つ。Go なら go-convention の develop-go-unit が、一つの層の単位をテスト、赤、実装、緑、整える、の順で仕上げる。

## 作業手順

### 1. 一つの場面を一つの受け入れテストへ写す

`references` があれば、この工程の最初に読む。

[内側から外側へ進むゲート](references/delivery-gates.md)を読み、対象の場面、永続化の要否、command か query か、パターンを資料から決める。決めた根拠として、資料の箇所、期待状態、実行した command と終了状態を記録する。場面が無ければ、コードもテストも変えずに止まる。

外部との境界を実 DB まで通すテストを、一つの場面につき一本書く。対象の機能がまだ無いことが理由で赤になることを確かめる。接続の失敗、設定の不足、無関係なテストの故障は、赤の証拠にしない。

### 2. ドメインを実装する

場面が業務の状態の変更か業務の判断を含むときに行う。業務知識の拒む理由と、ドメインモデルの状態とコマンドを、ドメインのテストへ写し、集約と値オブジェクトに実装する。業務の時刻と識別子は引数で受ける。業務規則の受ける場合、拒む場合、境界をここで網羅する。

テストを資料に合わせて弱めない。読み取りだけの場面、または単純なパターンの処理では、この工程を非該当として記録して次へ進む。

### 3. 永続化または読み取りを実装する

command では、論理データモデルの Before と After を、実 DB のリポジトリのテストへ写す。判断の材料を読む Find は、読むだけで判断しないことを確かめる。集合の条件は DB の宣言的な制約で守り、違反を業務の拒否へ翻訳することを確かめる。同時に起きる場面は、物理設計が決めた守り方で確かめる。

query では、読み取りの口の実装を実 DB で動かし、平らな読み取りモデルを確かめる。一覧、件数、検索、存在確認は Query の実装に置き、集約を復元しない。

選んだ DB で集合の条件を宣言できない、物理設計に分離レベルの指定が無い、のどちらかなら、ロックや事前の確認を発明せずに止まって資料へ返す。

### 4. usecase を実装する

呼ぶ集約とリポジトリか読み取りの口のテストが、すべて緑のときに行う。

usecase のテストは三つを置く。場面の成功の一本、途中で失敗したときに書き込みが残らないこと、Outbox を使うなら発生元の変更と要求の記録が同じトランザクションに残ること、である。usecase は材料を集めず、状態で分岐しない。集約を見つけ、コマンドを一回呼び、結果を適用するだけである。トランザクションは、物理設計の指定を渡して usecase が張る。業務規則と、下の層で確かめた Before と After を、ここで網羅し直さない。

下の層のテストが一つでも赤なら、usecase を実装しない。

### 5. 入口を実装して受け入れを通す

usecase のテストがすべて緑のときに行う。外からの入力を値オブジェクトへ変換して usecase の入力に詰め、結果を応答へ写す入口を実装する。業務の時刻は入口が時計から一度だけ取る。入口に業務の判断、計算、集約の復元を置かない。最初に書いた受け入れテストを実行し直し、緑にする。

受け入れテストだけを通す分岐や固定の値を足さない。緑にならなければ、最初に失敗した層へ戻る。

### 6. 追跡とゲートの結果を報告する

場面、業務知識、データモデルの Before と After について、資料の絶対 path と版、業務操作、期待状態、対応するテストを記録する。非該当の工程にも理由を書く。受け入れテストから各資料と各層のテストへ戻れ、実行した検査、実行しなかった検査、止まったゲートを分けて示す。

## 出力

一つの場面を完成させる実装と、受け入れ、ドメイン、永続化または読み取り、usecase のテストを返す。資料の所在と版、業務操作、期待状態からテストへの追跡を返す。各ゲートの合否、実行した command、検査しなかった範囲、止まった理由と資料への提案を返す。

## 停止条件

次のときは止まり、次の層へ進まない。止めたゲート、最初の失敗、必要な確認、変更したファイル、手を付けていない層を返す。

ユーザージャーニーの対象の場面が無いとき。資料が曖昧か、資料どうしが食い違い、業務操作や期待状態、永続化の範囲、command か query かが一つに決まらないとき。このときは推測で埋めず、問題と提案を資料の持ち主へ返す。論理データモデルが対象外とした永続化を、場面が必要とするとき。下の層のゲートが赤のとき。選んだ DB で集合の条件を宣言できないか、物理設計に必要な指定が無いとき。実 DB を使う検査を実行できないとき。

## 完了条件

一つの場面の受け入れテストが、外部との境界と実 DB を通して緑である。業務規則、永続化または読み取り、トランザクションが、それぞれのゲートで確かめられている。資料に無い振る舞い、推測で埋めた値、互換のための分岐、将来のための公開面を足していない。資料からテストへの追跡と、検査しなかった範囲を報告している。

## 使用例

典型例：「利用者が本を借りる」場面を受け入れテストにし、貸出の集約のテスト、貸出と出来事の Before と After の実 DB のテスト、usecase のテストの順に緑にし、最後に RPC の入口で受け入れを緑にする。

似て非なる例：貸出の一覧を表示する場面は読み取りだけなので、ドメインの工程を非該当とし、Query の実装の実 DB のテストから始める。

反例：返却期限の日を、資料に書かれていない「貸出日の翌日から数えて14日」と推測して実装する。資料の「貸出日の14日後」が何を起点にするかが曖昧なら、止まって資料の持ち主へ問う。

境界例：延滞にする場面で、資料が通知を「後で送る」と定めているなら、usecase のテストは延滞の記録と通知の要求が同じトランザクションに残ることを確かめる。通知を送る手順は別の場面として扱う。
