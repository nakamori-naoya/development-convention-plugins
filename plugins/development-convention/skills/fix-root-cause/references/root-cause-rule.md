# 症状から根本原因への追跡規律

## 三つの語

症状は、報告者が観測した結果と期待した結果の差である。症状は経路の出口で見えるが、原因の場所を示さない。

原因は、症状を起こす入力に対して期待状態と違う結果を作っている判断・変換・翻訳である。原因は一つの関数の一つの分岐まで特定する。

箇所は、原因を直すために変更する場所である。箇所は、症状を起こす入力が通るすべての呼び出し経路が経由する関数のうち、最も内側の一つを選ぶ。

## 期待状態の権威

期待状態を定めるのは、現在の`domain-rule`、`domain-model`、`rdb-logical-data-modeling`、`user-journey-bdd`と、それらを写した既存テストである。報告者の期待と資料の期待が食い違えば資料が正であり、報告者の期待は資料を変えるかの問いになる。どちらも期待状態を定めていない症状は不具合ではなく資料の欠落であり、推測で「正しい振る舞い」を実装しない。資料が曖昧で期待状態が一つに決まらないときも、止まって資料の持ち主へ問う。

資料は、絶対パスと版または観測時点、業務操作、期待状態で識別する。文書内IDは他文書と共有しない。

## 最も内側の一か所

経路の内側から外側へ、判断・変換・翻訳は次の順に並ぶ。

1. 値オブジェクトの生成（一つの値が有効であるための条件）
2. 集約の操作（操作時点の状態と材料で決まる判断）
3. 判断の材料の読み取り（リポジトリの Find）と、usecase の手順
4. 永続化の変換と、集合的制約違反の拒否理由への翻訳
5. 外部境界の入力変換と、拒否理由から転送形式への翻訳

原因がある段より外側で塞ぐと、その段を通る経路の数だけガードが要り、後から増えた経路には効かない。原因のある段の一か所で直せば、その段を経由するすべての経路が同じ変更で安全になる。同じ判断が複数の経路に複製されている場合は、複製そのものが原因であり、判断を内側の一か所へ寄せてから直す。

一経路だけを塞ぐガードは、報告された経路の症状を消すが、兄弟の経路に同じ症状を残す。修正の完了は「報告された経路が通る」ではなく「列挙した全経路が同じ一か所で直っている」で判定する。

## 再現テストの層

再現テストは、症状が現れる最も内側の層に置く。業務判断の誤りなら集約・値オブジェクトのテスト、永続化や集合的制約の誤りなら実DBのテスト、外部境界の変換や翻訳の誤りなら外部I/Fを実DBで駆動する受け入れテストである。既存テストが症状を捕えていれば新設しない。

再現テストの赤は、症状そのものが理由でなければならない。何を赤とみなすかは `develop-inside-out` の赤の定義に従う。

## 変更の大きさ

最小の変更とは、全経路を安全にする変更の候補のうち、変えた宣言と分岐が最も少ないものである。一経路だけを塞ぐ変更は候補に入らない。整形・改名・構造の変更・症状に関係しない改善は、原因の修正と分けて別の依頼にする。削除量や差分の行数を根本性の根拠にしない。

## 判断例

典型例：返却済みの貸出の本をもう一度返せる症状。返すを呼ぶ経路は利用者の RPC と窓口の一括返却の二本で、どちらも貸出の集約の返すを経由する。返却済みの状態の型が返すを拒む形で塞ぎ、二つの経路とも同じ拒否になる。

似て非なる例：貸出の期間を延長できないという報告。資料に延長の操作が無いので不具合ではなく、資料の欠落として返す。

反例：報告された RPC の経路にだけ「返却済みなら拒否」の分岐を足す。窓口の一括返却の経路に同じ症状が残る。

境界例：入口の変換が利用者番号と資料番号を取り違えている症状。経路は一本で、共通点はその変換の関数一つである。集約と値オブジェクトは正しいので触れず、変換の関数だけを直す。
