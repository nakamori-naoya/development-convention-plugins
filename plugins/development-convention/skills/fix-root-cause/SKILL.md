# fix-root-cause

**直すのは、症状を起こす入力が通るすべての呼び出し経路が経由する、最も内側の一か所である。** 一つの経路だけを塞ぐガードは足さない。報告された経路の症状は消えても、兄弟の経路と後から増える経路に同じ症状が残るからである。

## 不具合かどうかは資料で決まる

期待状態を定めるのは、現在の業務の資料（domain-rule、domain-model、rdb-logical-data-modeling、user-journey-bdd）と、それを写した既存のテストである。報告者の期待と食い違えば資料を正とし、報告者の期待は資料を変えるかの問いとして返す。資料もテストも期待状態を定めていなければ、不具合ではなく資料の欠落として返し、要求を足さない。資料が曖昧で期待状態が一つに決まらないときも、推測で選ばずに止まる。

## 再現テストを赤にしてから直す

症状が現れる最も内側の層に再現テストを一本置く。業務の判断の誤りなら集約か値オブジェクトのテスト、永続化や制約の誤りなら実 DB のテスト、入口の変換や翻訳の誤りなら入口から実 DB まで通すテストである。既存のテストが捕えていれば新しく書かない。赤は `develop-inside-out` の定義に従い、失敗の理由が報告された症状そのものであることを確かめる。再現しなければ、試した条件を返して止まる。

## 経路を辿り、一か所を選ぶ

症状を起こす関数の呼び出し元を、別の入口、定期処理、ほかの業務操作からの呼び出しも含めて外部との境界まで全部辿る。辿りきれない動的な呼び出しは、報告に残して進む。経路の内側から外側へは、値オブジェクトの生成、集約の操作、材料の読み取りと usecase の手順、永続化の変換と制約違反の翻訳、入口の変換と応答への翻訳、の順に並ぶ。全経路が経由する最も内側の箇所を直し、同じ判断が経路ごとに複製されていれば、複製そのものを原因として内側の一か所へ寄せてから直す。

変更は、全経路を安全にするもののうち、変える宣言と分岐が最も少ないものにし、整形や改名をついでに行わない。修正で既存のテストが赤になり、それが資料の期待状態を変えることを意味するなら、戻して止まる。修正の後は、再現テスト、関係する既存のテスト、ビルド、静的検査を通す。

## 止まるとき

期待状態が一つに決まらないとき、症状を再現できないとき、修正が資料の期待状態を変えるとき、直す箇所が生成コードか外部の package の中にあるとき（生成元か依存の更新を提案する）、修正の後に検査が失敗したときは止まる。要求の追加や複数の不具合の一括修正は別の依頼として返し、症状が複数あれば最初の一つだけを扱う。報告には、症状、期待状態の根拠、再現テスト、辿った経路、選んだ一か所とその理由、変更と検査、辿りきれなかった経路を書く。

## 例

「返却済みの本をもう一度返せてしまう」で、返すを呼ぶ経路が利用者の RPC と窓口の一括返却の二本なら、どちらも経由する集約の返すを、返却済みの状態の型が拒む形で直す。RPC の入口にだけ分岐を足すのは反例で、一括返却に症状が残る。入口の変換が利用者番号と資料番号を取り違えているなら、経路が一本でも直すのはその変換の関数である。「貸出の期間を延長できない」は資料に延長の操作が無いので、資料の欠落として返す。
