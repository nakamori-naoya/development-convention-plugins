# fix-root-cause

[工程順序の定義](playbook.yml)を最初に読み、同じagentが\`steps\`を宣言順に実行する。YAMLは工程順序を決め、各工程の判断内容と根拠はこの本文と参照資料を実読して評価する。失敗時は成功扱いせず停止して、完了工程、根拠、未決を残し、再開時は最初の未完了工程から続ける。

不具合の報告を受け取り、症状が現在の業務の資料と食い違う不具合であることを確定し、症状を再現するテストを赤にし、症状を起こす入力が通るすべての呼び出し経路が経由する一か所を最小の変更で直して、そのテストと既存テストを緑にする。

この skill は、症状から根本原因の一か所へ辿り、全経路を同じ変更で安全にする。要求や振る舞いの追加、資料の欠落の補完、責務の再配置、症状に関係しない整形・改名・構造の変更、複数の不具合の一括修正は行わない。

## 入力

- 対象repositoryと、修正の対象になりうるコード範囲の絶対パス。
- 症状の報告。与えた入力または操作、観測した結果、期待した結果を含むこと。
- 現在の`domain-rule`、`domain-model`、`rdb-logical-data-modeling`、`user-journey-bdd`のうち症状に関係するもの。この入口では、これらを業務の資料と呼ぶ。各資料の版または観測時点。
- 既存テストと、テスト・ビルド・静的検査の実行方法。
- 対象言語で関数・操作の呼び出し元を検索する手段（参照検索tool、または検索コマンド）。
- 修正まで依頼されているか、原因の特定と修正候補の提示までか。
- `references`: 追加で従う資料の絶対path配列。任意。手順の最初に読み、以降の判断でこの規約と併せて従う。

プロジェクト固有の規約（置き場、命名、追加で従う資料）は、対象repositoryのAGENTS.md / CLAUDE.mdと`references`で渡される。この入口は既定値を持たず、指示文へ展開もしない。

各資料のIDは文書内だけで有効とする。追跡は資料の絶対パスと版、業務操作、期待状態の組で記録し、別資料の同じ番号を同一事項とみなさない。

## 開始条件

症状と、それを起こす入力または操作を一つ識別できる場合に開始する。症状が複数あれば、一つずつ別の依頼として扱い、最初の一つだけを対象にする。

## 判断基準

報告された症状は、現在の業務の資料か、それを写した既存のテストが、その入力に対する期待状態を一つに定めているときだけ、不具合として扱う。定めていなければ資料の欠落として返し、要求を足さない。資料が曖昧で期待状態が一つに決まらないときも、推測で「正しい振る舞い」を選ばずに止まり、資料の持ち主へ問う。

再現テストは、修正の前に、対象の症状が理由で赤になっていなければならない。何を赤とみなすかは `develop-inside-out` の赤の定義に従い、この入口では、その失敗の理由が報告された症状そのものであることを確かめる。赤を確かめてから直す。既存のテストが症状を捕えていれば、新しく書かない。

直す箇所は、症状を起こす入力が通るすべての呼び出し経路が経由する箇所のうち、最も内側の一か所にする。業務の判断なら集約か値オブジェクト、翻訳なら境界の対応表、変換なら変換の関数である。一つの経路だけを塞ぐガードは足さない。後から増えた経路には効かないからである。

変更は、全経路を安全にする変更のうち、変える宣言と分岐が最も少ないものにする。整形、改名、構造の変更を「ついで」に行わず、別の依頼として返す。

## 作業手順

### 1. 症状と期待状態を業務の資料へ固定する

`references` があれば、この工程の最初に読む。

適用条件: 症状の報告と、関係する業務の資料の候補がある。

必須行動: [症状から根本原因への追跡規律](references/root-cause-rule.md)を読み、症状の入力・観測結果・期待結果を記録する。期待状態を定める資料の絶対パス、版または観測時点、業務操作、期待状態、またはそれを写した既存テストの絶対パスとテスト名を記録する。資料間のID番号を共有識別子として扱わない。

成功判定: 症状に対する期待状態が、資料または既存テストのどちらかから一つに決まり、報告者の期待と資料の期待が一致している。

失敗時: 資料もテストも期待状態を定めていなければ、不具合ではなく資料の欠落として返して止まる。報告者の期待と資料の期待が食い違えば、資料の期待を正とし、報告者の期待は資料を変えるかの問いとして未決に残す。

### 2. 症状を再現テストで赤にする

適用条件: 期待状態が一つに決まっている。

必須行動: 既存テストが症状を捕えていればそれを使う。無ければ、症状を起こす入力と資料の期待状態を写したテストを、症状が現れる最も内側の層（業務判断なら集約や値オブジェクトのテスト、永続化なら実DBのテスト、外部境界の変換なら受け入れテスト）に一本置く。テストが対象の症状の理由で赤になることを確認する。

成功判定: 再現テストが赤で、失敗の理由が症状そのものであり、テスト名または追跡情報から資料の絶対パスと版、業務操作、期待状態へ戻れる。

失敗時: 赤にならなければ症状の再現条件が違う。入力と前提状態を報告と突き合わせて直し、それでも赤にならなければ再現できない旨と試した条件を返して止まる。

### 3. 呼び出し経路を列挙する

適用条件: 症状を起こす関数・操作・問い合わせを再現テストから特定できる。

必須行動: その関数・操作の呼び出し元を、入力の検索手段で外部境界まで全部辿る。経路ごとに、入力の由来、経由する関数、症状に至る条件を記録する。報告された経路だけでなく、同じ関数を通る他の経路（別の外部境界、定期処理、他の業務操作からの呼び出し）を含める。

成功判定: 症状を起こしうる経路がすべて列挙され、各経路が経由する関数の列が記録されている。

失敗時: 動的な呼び出しや生成コードで列挙が不完全になる場合は、静的に見つかる範囲を経路とし、見つけられない経路がありうることを未決に残して進む。

### 4. 共通点の一か所を決める

適用条件: 経路が列挙されている。

必須行動: 全経路が経由する関数のうち最も内側の一か所を修正箇所に選ぶ。業務判断の誤りなら集約または値オブジェクト、拒否の翻訳の誤りなら境界の対応表、入力変換の誤りなら変換関数が候補になる。選んだ箇所と、選ばなかった外側の箇所（各経路の入口など）を理由付きで記録する。

成功判定: 選んだ一か所を直せば、列挙した全経路で症状が消えることを経路の記録から説明できる。

失敗時: 全経路が経由する一か所が無く、同じ判断が経路ごとに複製されている場合は、複製そのものを根本原因とし、判断を最も内側の一か所へ寄せてから直す。影響する経路と変更範囲を判断記録に明示して進む。

### 5. 最小の変更で緑にする

適用条件: 修正箇所が一つに決まっている。

必須行動: 依頼範囲で分ける。修正まで依頼されていれば、選んだ一か所を全経路を安全にする変更のうち最小のもので直し、再現テスト、関係する既存テスト、ビルド、静的検査を実行する。原因の特定までの依頼なら、コードを変えずに修正箇所と変更案を判断記録へ残し、手順6へ進む。

成功判定: 修正まで依頼された場合は、再現テストが緑になり、既存テスト、ビルド、静的検査が成功し、変更が選んだ一か所とそのテストに閉じている。原因の特定までの場合は、修正箇所と変更案が経路の記録から説明でき、コードが変わっていない。

失敗時: 修正で既存テストが赤になり、その赤が資料の期待状態を変える意味を持つなら、修正を戻して止まる。赤の理由が既存テストの誤りなら、資料と突き合わせた根拠を記録して直す。

### 6. 根拠と変更を報告する

適用条件: 修正または原因の特定が完了した。

必須行動: 症状、期待状態の根拠（資料の絶対パスと版、業務操作、期待状態、または既存テスト）、再現テスト、列挙した経路、選んだ一か所とその理由、変更ファイル、実行した検査、未確認の経路と未決を報告する。

成功判定: 利用者が症状から資料、再現テスト、経路、修正箇所、差分まで辿れ、一経路だけの対処になっていないことを確認できる。

失敗時: 削除量や差分の行数を根本性の根拠にしない。列挙しきれなかった経路を未確認として返す。

## 出力

- 症状、期待状態の根拠、再現テスト、呼び出し経路、修正箇所の判断記録。
- 修正まで依頼された場合は、一か所の変更と緑になった再現テスト。
- 実行した検査、変更しなかった範囲、業務の資料へ戻す問い、未確認の経路。

## 停止条件

期待状態を、資料からも既存のテストからも一つに定められないときは止まる。不具合ではなく資料の欠落なので、その旨を返す。再現テストを実行できない（実 DB など必要な実行の手段が無い）とき、または症状を再現できないときも止まる。

修正で既存のテストが赤になり、その赤が資料の期待状態を変えることを意味するなら、修正を戻して止まり、変えようとしている振る舞いと必要な決定を返す。修正する箇所が生成コードか外部の package の内部にあるなら、生成元か依存の更新を提案して止まる。修正の後に対象のテスト、ビルド、静的検査が失敗したら、失敗と変えていない範囲を返して止まる。

依頼が次のことを求めているときも、行わずに止まり、別の依頼として返す。現在の業務の資料へ新しい要求、振る舞い、受け入れ条件を足すこと、症状に関係しない整形、改名、責務の再配置、構造の変更、複数の不具合を一度に直すことである。これらは不具合の修正ではなく、根本原因の一か所を直すという範囲を超えるからである。

止まるときは、確定した症状・期待状態・経路の記録を破棄せず、止めた工程、必要な確認、変更済みファイル、未着手の範囲を返す。

資料が曖昧で期待状態が一つに決まらないときは、推測で埋めずに止まる。何が決まらないかと、資料をどう直せば決まるかの提案を返す。

コードの側の次の揺れは、止まらずに規則で決め、判断記録に残す。全経路が経由する一か所が無く、同じ判断が経路ごとに複製されているなら、複製そのものを原因とし、判断を最も内側の一か所へ寄せてから直す。動的な呼び出しや生成コードで経路を列挙しきれないなら、静的に見つかる範囲を経路とし、見つけられない経路がありうることを未確認として報告する。再現テストを置く層は、症状が現れる最も内側の層にする。

## 完了条件

- 再現テストが修正前に症状の理由で赤、修正後に緑である。
- 症状を起こす全経路が、同じ一か所の変更で直っている。
- 一経路だけを塞ぐガード、症状に関係しない変更、資料に無い振る舞いを加えていない。
- 期待状態が資料または既存テストへ追跡できる。
- 症状から差分までの追跡、実行した検査、未確認の経路を報告している。

## 使用例

典型例：「返却済みの貸出の本をもう一度返せてしまう」という症状。資料は返却済みの本を返すことを拒む。返すを呼ぶ経路は、利用者の RPC と、窓口の一括返却の二本である。RPC の入口に状態の検査を足すのではなく、返却済みの状態の型が返すを拒む形で塞ぎ、二つの経路とも同じ拒否になる。

似て非なる例：「貸出の期間を延長できない」は、資料に延長の操作が無い。不具合ではなく資料の欠落として返し、操作を足さない。

反例：報告された RPC の経路にだけ「返却済みなら拒否」の分岐を足す。窓口の一括返却の経路に同じ症状が残る。

境界例：症状の経路が一本しか無くても、直すのは最も内側の一か所である。入口の変換が利用者番号と資料番号を取り違えているなら、共通点はその変換の関数一つで、集約には触れない。
