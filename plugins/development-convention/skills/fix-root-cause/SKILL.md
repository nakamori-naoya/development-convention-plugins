# fix-root-cause

**直すのは、症状を起こす入力が通るすべての呼び出し経路が経由する、最も内側の一か所である。** 一つの経路だけを塞ぐガードは足さない。報告された経路の症状は消えても、兄弟の経路と後から増える経路に同じ症状が残るからである。

## 不具合かどうかは資料で決まる

症状は、観測した結果と期待した結果の差である。期待状態を定めるのは、現在の業務の資料（domain-rule、domain-model、rdb-logical-data-modeling、user-journey-bdd）と、それを写した既存のテストである。報告者の期待と資料の期待が食い違えば資料を正とし、報告者の期待は資料を変えるかの問いとして返す。資料もテストも期待状態を定めていなければ、不具合ではなく資料の欠落として返し、要求を足さない。資料が曖昧で期待状態が一つに決まらないときも、推測で「正しい振る舞い」を選ばずに止まる。

## 再現テストを赤にしてから直す

症状が現れる最も内側の層に、再現テストを一本置く。業務の判断の誤りなら集約か値オブジェクトのテスト、永続化や集合の制約の誤りなら実 DB のテスト、入口の変換や翻訳の誤りなら入口から実 DB まで通すテストである。既存のテストが症状を捕えていれば新しく書かない。何を赤とみなすかは `develop-inside-out` の赤の定義に従い、ここでは失敗の理由が報告された症状そのものであることを確かめる。赤にならなければ再現条件が違うので、報告と突き合わせて直し、それでも再現しなければ試した条件を返して止まる。

## 経路を辿り、一か所を選ぶ

症状を起こす関数の呼び出し元を、外部との境界まで全部辿る。報告された経路だけでなく、別の入口、定期処理、ほかの業務操作からの呼び出しも含める。動的な呼び出しや生成コードで辿りきれない経路は、見つからない経路がありうることとして報告に残して進む。

経路の内側から外側へは、値オブジェクトの生成、集約の操作、判断の材料の読み取りと usecase の手順、永続化の変換と制約違反の翻訳、入口の変換と応答への翻訳、の順に並ぶ。全経路が経由する箇所のうち最も内側の一つを直す。同じ判断が経路ごとに複製されていて共通の一か所が無いなら、複製そのものが原因なので、判断を内側の一か所へ寄せてから直す。

変更は、全経路を安全にする変更のうち、変える宣言と分岐が最も少ないものにする。整形、改名、構造の変更をついでに行わず、別の依頼として返す。修正で既存のテストが赤になり、それが資料の期待状態を変えることを意味するなら、修正を戻して止まる。既存のテストの誤りなら、資料と突き合わせた根拠を記録して直す。修正の後は、再現テスト、関係する既存のテスト、ビルド、静的検査を通す。

## 止まるとき

期待状態が一つに決まらないとき、再現テストを実行できないか症状を再現できないとき、修正が資料の期待状態を変えるとき、直す箇所が生成コードか外部の package の中にあるとき（生成元か依存の更新を提案する）、修正の後に検査が失敗したときは止まる。要求の追加、症状に関係しない変更、複数の不具合の一括修正を求められたら、別の依頼として返す。症状が複数あれば、最初の一つだけを扱う。

報告には、症状、期待状態の根拠（資料の箇所と版、または既存のテスト）、再現テスト、辿った経路、選んだ一か所とその理由、変更したファイル、実行した検査、辿りきれなかった経路を書く。原因の特定だけを頼まれたなら、コードを変えずに修正の箇所と変更の案を返す。

## 例

「返却済みの貸出の本をもう一度返せてしまう」という症状で、返すを呼ぶ経路は利用者の RPC と窓口の一括返却の二本、どちらも貸出の集約の返すを経由する。返却済みの状態の型が返すを拒む形で直せば、二つの経路とも同じ拒否になる。RPC の入口にだけ「返却済みなら拒否」の分岐を足すのは反例で、一括返却に症状が残る。入口の変換が利用者番号と資料番号を取り違えているなら、経路が一本でも共通の一か所はその変換の関数で、集約には触れない。「貸出の期間を延長できない」は資料に延長の操作が無いので、不具合ではなく資料の欠落として返す。
