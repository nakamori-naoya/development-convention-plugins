# apply-yagni

基準は一つだけである。**現在の業務の資料と、その振る舞いを写したテストが、この公開シンボルを呼ぶか。** 呼ぶなら keep、呼ばないなら reject にする。業務の資料とは、対象に関係する現在の domain-rule、domain-model、rdb-logical-data-modeling、user-journey-bdd である。公開シンボルは、外から名前で使える契約（公開の関数、型、メソッド、外部 I/F、設定項目、イベントの契約）で、非公開の変換や接続は対象外である。

将来使う、汎用にしたい、便利、一般的な推奨は、どれも根拠にならない。テストのためだけに公開を増やすこと（`export_test.go` のように内部をテストへ晒すことを含む）も reject である。テストが呼ぶことを根拠にできるのは、そのテストが業務の資料の振る舞いを写しているときだけだからである。資料の外の技術的なテストが持つ生成したケースの ID や、同じ振る舞いを確かめるためのランダムな入力も、新しい公開面の根拠にしない。

shim、互換の分岐、deprecated の温存、旧い名前への委譲、新旧の二重書き込みは、資料やテストが呼んでいても常に reject にする。互換を残すと同じことをする経路が二つになり、どちらが正しいかを毎回確かめることになるからである。資料が旧い形を呼んでいるなら、資料とテストを通常の形へ更新する必要を未決として返す。

## 追跡が足りないとき

資料かテストへの追跡が見つからない候補は reject と判定し、欠けた資料かテストを未決に残す。除去まで頼まれていても、この候補は除去しない。根拠が欠けていることは分かっても、無用だと確かめたわけではないからである。reject は「現在の根拠が無い」という事実であり、推測ではない。

## 適用する

新しく書くときは reject を作らない。既存のコードからの除去を頼まれたときは、reject と、その公開面だけを支えるコードとテストを削り、keep の振る舞いを変えない。判定だけの依頼ならコードを変えない。削ると keep が壊れるなら、隠れた呼び出しを記録して判定に戻り、新しい互換層で検査を通さない。除去の後は対象のテスト、ビルド、静的検査を通す。

## 止まるとき

対象の範囲、業務の資料、候補のどれも識別できないとき、業務の資料の候補が複数あり現在の版が分からないとき、候補が公開面かどうかを確かめられないとき、reject の候補が既存か新規かを対象コードで確かめられないときは、推測で決めずに止まって問う。要求の追加、層やトランザクションの設計、一般的なコードレビューを求められたら、この判定の範囲ではないので別の依頼として返す。

報告には、候補ごとの keep か reject、根拠の資料の箇所と版、対応するテスト、変更したファイル、実行した検査、資料へ戻す問いを書く。削った量や行数を根拠にしない。

## 例

本を借りる場面とそのテストが呼ぶ `BorrowBook` は keep、同じ資料が一度も呼ばない汎用の `UpsertLoan` は reject である。将来まとめて貸すかもしれないとして残した `BulkBorrow` と空の拡張の interface も reject である。非公開の行の変換関数は、この判定の対象外である。テストで内部の状態を見るために足した公開の getter は、業務の資料が呼ばないので reject にし、公開の振る舞いで観測する形へ戻す。
