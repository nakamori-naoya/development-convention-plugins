# apply-yagni

[工程順序の定義](playbook.yml)を最初に読み、同じagentが\`steps\`を宣言順に実行する。YAMLは工程順序を決め、各工程の判断内容と根拠はこの本文と参照資料を実読して評価する。失敗時は成功扱いせず停止して、完了工程、根拠、未決を残し、再開時は最初の未完了工程から続ける。

対象コードの公開シンボルを、現在の正式な定義資料とその振る舞いを写したテストが呼ぶかで判定し、根拠のない公開シンボルを対象範囲から除く。

この skill は、現在必要な公開面だけを残す。将来価値の予測、要件の追加、層の配置、実装工程の進行、一般的なコード品質の改善は行わない。

## 入力

- 対象repositoryと、判定または変更するコード範囲の絶対パス。
- 現在の`domain-rule`、`domain-model`、`rdb-logical-data-modeling`、`user-journey-bdd`のうち対象に関係する正式な定義。各資料の版または観測時点。
- 正式な定義の振る舞いを写したテストと、資料からテストへの追跡情報。
- 候補となる公開シンボル。公開関数、公開型、公開メソッド、外部I/F、設定項目、イベント契約を含む。
- 判定だけか、不要な公開シンボルの除去まで依頼されているか。
- `references`: 追加で従う資料の絶対path配列。任意。手順の最初に読み、以降の判断でこの規約と併せて従う。

プロジェクト固有の規約（置き場、命名、追加で従う資料）は、対象repositoryのAGENTS.md / CLAUDE.mdと`references`で渡される。この入口は既定値を持たず、指示文へ展開もしない。

## 開始条件

対象範囲、現在の正式な定義資料、候補公開シンボルを識別できる場合に開始する。資料が欠けて要否を判定できないシンボルは、「あると便利」で保持せず`reject`の判定にし、欠けた資料を未決として返す。

## 作業手順

### 1. 現在の正式な定義を固定する

`references` があれば、この工程の最初に読む。

適用条件: 対象に関係する資料を列挙できる。

必須行動: [公開シンボルの根拠規律](references/evidence-rule.md)を読み、各資料の絶対パス、版または観測時点、対象業務操作、期待状態を記録する。資料間のID番号を共有識別子として扱わない。

成功判定: 判定に使う資料集合と、意図的に対象外とする資料を説明できる。

失敗時: 正式な定義の候補が複数あり、どれが現在の版か分からなければ、推測で選ばずに止まり、どれを正とするかを資料の持ち主へ問う。候補の間で分類が変わるシンボルを添える。正式な定義の候補が一つも無ければ、判定の根拠が無いので止まる。

### 2. 資料とテストの対応を検査する

適用条件: 正式な定義から導かれたとされるテストがある。

必須行動: テストごとに資料の所在と版、業務操作、期待状態への追跡を確認する。資料外の補助的・技術的テストが生成したケースIDを持つことと、テストデータの識別子・時刻をランダム化することを区別する。前者は同じテスト範囲で一意かつ保存後に安定している場合、後者は既存の同じ振る舞いを複数入力で確かめる場合に限り許容する。どちらからも新しい業務分岐や公開シンボルの必要性を導かない。

成功判定: 各テストが正式な定義にある振る舞いを写しているか、資料にないテストかを分類できる。

失敗時: 追跡不能なテストを公開シンボルの根拠に使わない。削除もせず、手順3で要否不明として扱う対象に含め、資料へ戻す未決として記録して進む。

### 3. 公開シンボルを保持または拒否へ分類する

適用条件: 候補公開シンボルと、正式な定義に追跡できるテストの呼び出しを確認できる。

必須行動: 次の一つの基準だけを適用する。

> 現在の正式な定義資料と、その振る舞いを写したテストが、この公開シンボルを呼ぶか。

直接呼ぶ、または現在の振る舞いを成立させる通常の公開契約として一意に必要なら`keep`とする。どちらからも呼ばれない、要否が不明、将来利用、汎用化、便利さ、一般的な推奨だけが理由なら`reject`とする。shim、互換分岐、deprecated温存、旧名委譲は、資料とテストに呼び出しがあっても常に`reject`とする。

候補ごとに、公開面か、既存か、正式な定義資料のどの箇所が呼ぶか、その振る舞いを写したどのテストが呼ぶかを、実資料・実コード・実テストの箇所で記録する。将来利用、互換形、補助テストのcase ID、ランダム入力、新しい業務分岐は根拠と混同しない。booleanを並べた入力から分類を決めるスクリプトやstdoutを決定の基準資料にせず、この証拠を同じ担当が読んで`keep`または`reject`を判断する。

追跡が不足する候補は要否不明として`reject`の判定にし、欠けた正式な定義またはテストと影響する候補を未決へ残す。除去まで依頼されていても、その候補は根拠が欠けているだけで無用と確かめたわけではないので除去せず、判定だけを返す。既存の`reject`は削除対象、新規の`reject`は作らない判断とする。候補が既存か新規かは、対象コードに現在あるかで決める。候補が公開面かどうかを確かめられない場合と、`reject` の候補で対象コードを読めず既存か新規か（削除するか作らないか）を確かめられない場合は、推測で扱いを決めずに止まり、確かめる手段を利用者へ問う。`keep` の候補は、既存か新規かで行動が変わらないので止まらない。

成功判定: すべての候補が`keep`または`reject`の一つになり、`keep`には資料とテスト、`reject`には根拠不在を示せる。

失敗時: 「確認すれば作ってよい」「技術的に必要かもしれない」という例外を作らない。公開する必要性が確定しなければ`reject`とし、正式な定義を変更するかを利用者へ返す。

### 4. 互換用の公開面を拒否する

適用条件: 置換済みまたは削除予定の公開シンボル、旧呼び出しを残す分岐がある。

必須行動: shim、互換分岐、deprecatedの温存、旧名の委譲、二重書き込みを常に削除対象にする。通常の公開シンボルへ置き換え、現在の正式な定義とテストがその通常シンボルを呼ぶ場合にだけ通常シンボルを保持する。

成功判定: 互換用コードが資料やテストの呼び出しを理由に保持されず、対象範囲から除かれている。

失敗時: 「念のため」や現行利用を理由に互換形を残さない。正式な定義が互換形を呼んでいる場合も互換形は`reject`にし、通常の公開シンボルへ正式な定義とテストを更新する必要があることを未決として返す。正式な定義の更新はこの能力の出力ではない。

### 5. 対象範囲へ適用する

適用条件: 全候補の分類が完了し、変更の依頼範囲が確定している。

必須行動: 新規実装中は`reject`を作らない。既存コードからの除去まで依頼されている場合は、対象範囲の`reject`と、その公開面だけを支えるコード・テストを削除する。判定だけの依頼ではコードを変更しない。`keep`の振る舞いを変えない。

成功判定: 対象範囲の公開シンボルがすべて`keep`であり、対象テスト、ビルド、静的検査が成功する。

失敗時: `reject`の削除が`keep`を壊す場合は、隠れた呼び出しを記録して分類へ戻る。新しい互換層で検査を通さない。

### 6. 根拠と変更を報告する

適用条件: 分類または変更が完了した。

必須行動: 各公開シンボルの分類、資料の絶対パスと版、対応テスト、変更ファイル、実行検査、未確認事項を報告する。

成功判定: 利用者が各`keep`を正式な定義まで辿れ、各`reject`に現在の根拠がないことを確認できる。

失敗時: 削除量やコード行数をYAGNIの根拠にしない。追跡不能な判断を未確認として返す。

## 出力

- 公開シンボルごとの`keep`または`reject`、根拠資料、対応テストを持つ判断記録。
- 変更まで依頼された場合は、`reject`を除去し、`keep`だけが残る対象コード。
- 実行した検査、変更しなかった範囲、正式な定義へ戻す問い。

## 停止条件

対象の範囲、正式な定義資料、候補の公開シンボルのどれかを一つも識別できないときは止まる。`reject` を除去すると `keep` が壊れ、隠れた呼び出しの意味が確かめられていないときは、除去を止め、判定と隠れた呼び出しを返す。除去の後に対象のテスト、ビルド、静的検査が失敗したら、新しい互換層で通さずに、失敗と変えていない範囲を返して止まる。

依頼が次のことを求めているときも、行わずに止まり、それを持つ別の依頼として返す。現在の正式な定義へ新しい要求、振る舞い、受け入れ条件を足すこと、層、ディレクトリ、トランザクションの境界を設計すること、可読性、性能、セキュリティ一般のレビューである。この skill が判定するのは公開シンボルの要否だけだからである。非公開の変換、接続、言語の構文は公開シンボルではないので、個別に並べて判定しない。

止まるときは不明な公開面や互換形を保持理由へ昇格させず、止めた判断、必要な正式な定義、未変更範囲を返す。

正式な定義の候補が複数あり現在の版が分からないとき、候補が公開面かどうかを確かめられないときも、推測で埋めずに止まって問う。

次の場合は止まらず、規則で判定する。公開シンボルと資料やテストの追跡が見つからないなら、現在の根拠が無いので `reject` と判定し、欠けた資料かテストを未決に残す。この場合、除去まで依頼されていても除去はせず、判定だけを返す。正式な定義が互換形を呼んでいて移行が決まっていないなら、互換形は `reject` にし、正式な定義とテストを更新する要否を未決として返す。

`reject` の判定は「現在の根拠が無い」という事実であり、推測ではない。

## 完了条件

- 対象範囲の公開シンボルが、現在の正式な定義とそれを写したテストから追跡できる`keep`だけになっている。
- 要否不明、将来用、汎用化、便利さだけを根拠とする公開面がない。
- shim、互換分岐、deprecated温存を例外扱いしていない。
- 生成したテストケースIDとランダム化した入力値を区別し、どちらも新しい業務振る舞いを正当化していない。
- 判断、変更、検査、未確認事項を報告している。

## 使用例

典型例：本を借りる場面とそのテストが呼ぶ `BorrowBook` は `keep` にし、同じ資料が一度も呼ばない汎用の `UpsertLoan` は `reject` にする。

似て非なる例：非公開の DB の行の変換関数は外へ公開されないので、この判定の対象外である。要否は呼び出し元の実装の責務で判断する。

反例：将来まとめて貸すかもしれないとして、使われていない公開の `BulkBorrow` と空の拡張の interface を残す。現在の正式な定義とテストが呼ばないので拒否する。

境界例：資料の外の技術的なテストには、一意なケースの ID を生成して保存できる。利用者番号を毎回ランダムに作る入力のテストも、本を借りる同じ振る舞いを確かめるだけなら許す。ケースの ID や入力の値が特定の条件のときだけ動く公開メソッドを足した時点で、資料に無い振る舞いなので拒否する。
