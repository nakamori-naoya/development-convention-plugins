# apply-yagni

基準は一つだけである。**現在の業務の資料と、その振る舞いを写したテストが、この公開シンボルを呼ぶか。** 呼ぶなら keep、呼ばないなら reject にする。業務の資料は、対象に関係する現在の domain-rule、domain-model、rdb-logical-data-modeling、user-journey-bdd である。公開シンボルは外から名前で使える契約（公開の関数、型、メソッド、外部 I/F、設定項目、イベントの契約）で、非公開の変換や接続は対象外である。

将来使う、汎用にしたい、便利、一般的な推奨は根拠にならない。テストのためだけに公開を増やすこと（`export_test.go` のように内部をテストへ晒すことを含む）も reject で、テストが根拠になるのは業務の資料の振る舞いを写しているときだけである。資料の外の技術的なテストが持つ生成したケースの ID やランダムな入力も、新しい公開面の根拠にしない。shim、互換の分岐、deprecated の温存、旧い名前への委譲、新旧の二重書き込みは、資料やテストが呼んでいても常に reject にし、資料とテストを通常の形へ更新する必要を未決として返す。互換を残すと同じことをする経路が二つになるからである。

追跡が見つからない候補は reject と判定し、欠けた資料かテストを未決に残す。除去まで頼まれていても、この候補は除去しない。根拠が欠けていると分かっただけで、無用だと確かめたわけではないからである。

新しく書くときは reject を作らない。除去を頼まれたときは、reject とその公開面だけを支えるコードとテストを削り、keep の振る舞いを変えず、対象のテスト、ビルド、静的検査を通す。削ると keep が壊れるなら、隠れた呼び出しを記録して判定に戻り、新しい互換層で通さない。

## 止まるとき

業務の資料の候補が複数あり現在の版が分からないとき、候補が公開面かどうかを確かめられないとき、reject の候補が既存か新規かを確かめられないときは、推測で決めずに問う。要求の追加、層の設計、一般的なコードレビューは別の依頼として返す。報告には、候補ごとの keep か reject、根拠の資料の箇所と版、対応するテスト、変更したファイル、資料へ戻す問いを書き、削った量を根拠にしない。

## 例

本を借りる場面とそのテストが呼ぶ `BorrowBook` は keep、どこからも呼ばれない汎用の `UpsertLoan` と、将来のための `BulkBorrow` は reject である。テストで内部の状態を見るために足した公開の getter も reject にし、公開の振る舞いで観測する形へ戻す。
