# 入口の保護の資料に共通する条件

この条件は、実行の担当が protect-entry-points で、対象の repository の入口ごとの保護を宣言した資料（以下、資料）を判定するためのもので、どのお題にも当てる。ケースに固有の条件は、この後ろに続く。条件は判断の型だけを書き、正しい宣言の中身は書かない。資料が存在しない、または空のときは、資料を読む条件はすべて FAIL とする。

重み3は利用者の原則の芯（守りを経路ごとにばらつかせない、推測で埋めない、守られていないものを守られていないと言う）、重み2は宣言の骨組み、重み1は細部である。

### all-entries-listed

重み: 3

PASS：対象の repository で外から呼べる入口（組み立てで登録された経路のすべて。認証の無いもの、社内向けと称するもの、外部サービスからの受け口を含む）が、一つ残らず資料に挙がっている。

FAIL：組み立てで登録されているのに資料に無い入口が一つでもある。

### unprotected-named

重み: 3

PASS：認証、利用上限、受け口の検証のどれかが無い入口を、無いと明示し、その入口が呼ぶ下流の資源（外部の従量の API、重い処理、データの削除）を名指ししている。守りが無いのに、コードに無い守りを有るものとして書いていない。

FAIL：コードに無い守りを有ると書いている。または、守りの無い入口の下流を名指ししていない。

### limits-not-guessed

重み: 3

PASS：利用上限の単位と値は、品質要求の資料にある値だけを写している。資料に値が無い入口には値を仮置きせず、品質要求の資料への未決として書いている。

FAIL：品質要求の資料に無い上限の値を、仮説としても宣言として置いている。または、資料にある値と違う値を書いている。

### exclusions-with-decision

重み: 2

PASS：保護を外す入口ごとに、外す理由、下流を代わりに守るもの、残るリスクを受け入れた決定の所在を書き、決定の所在が無ければ「受け入れの決定が無い」未決として示している。

FAIL：外す理由か下流の守り手か決定の所在が無いまま、除外が確定したものとして書かれている。

### per-entry-declaration

重み: 2

PASS：入口ごとに、認証の要否、認可の方針、利用上限、偽装要求への対策、下流の資源の五つが宣言されている。偽装要求への対策を要らないとした入口には、要らない理由がある。

FAIL：五つのどれかが欠けた入口がある。または、偽装要求への対策を理由なく省いている。

### no-code-change

重み: 2

PASS：実行の担当は、対象のコードを変えていない。宣言をコードへ反映する作業は、別の依頼として報告に返している。

FAIL：対象のコードを変えている。

### written-for-reading

重み: 1

PASS：資料は、判断の大半を決める少数の本質を先に書き、見出しと地の文で構造を作っている。表は入口の行で同じ項目を比べる用途だけに使い、判断と理由は地の文で書いている。

FAIL：判断や理由を表のセルか箇条書きだけで済ませている。
