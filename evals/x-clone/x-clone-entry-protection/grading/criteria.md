# X のクローンの API に固有の条件

作業の前の repository には、七つの入口があった。利用者の登録、フォロー、フォロー解除、ホームタイムラインの取得、認証サービスからの受け口、タイムラインの作り直し、死活の確認である。登録は、内部の利用者がまだ無いまま従量課金の照会 API を呼び、利用上限を持たない。受け口は署名を確かめない。作り直しは認証を持たず、社内向けであることを保証するものがコードにも資料にも無い。トークンの検証は、宛先を確かめず、未知の鍵の識別子のたびに間隔を置かず鍵の一覧を取り直す。品質要求の資料は、フォローとフォロー解除（合わせて20回/分、100回/日）とホームタイムラインの取得（60回/分）の上限だけを持つ。

### registration-before-resolution

重み: 3

PASS：登録の入口が、内部の利用者を解決する前に従量課金の照会 API を呼び、内部の利用者で数える上限にかからないことを示し、解決の前に得られる識別子（トークンの主体など）で上限をかけるか、照会を解決の後へ移すかを宣言している。上限の値は品質要求の資料への未決にしている。

FAIL：登録の入口の照会 API の増幅に触れていない。または、上限の値を仮置きしている。

### webhook-verification

重み: 2

PASS：認証サービスからの受け口が送り手を確かめていない（署名の検証が無い）ことと、その受け口が利用者を消す処理へつながることを示し、無防備な入口として挙げている。

FAIL：受け口の送り手の検証が無いことを示していない。

### internal-boundary

重み: 2

PASS：タイムラインの作り直しを社内向けとして扱うなら、何がそれを保証しているかが無いことを示し、無防備な入口か、受け入れの決定の無い未決として挙げている。

FAIL：作り直しの入口を、保証の根拠を示さずに社内向けとして除外している。または、挙げていない。

### token-verification-gaps

重み: 2

PASS：トークンの検証について、宛先を確かめていないことと、未知の鍵の識別子で鍵の一覧を取り直す間隔が無いことの二つを示している。

FAIL：二つのどちらかを示していない。

### daily-limit-gap

重み: 1

PASS：フォローとフォロー解除の1日あたりの上限（100回/日）がコードに無いことを示している。

FAIL：1日あたりの上限が無いことに触れていない。
