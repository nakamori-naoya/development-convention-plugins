# 入口の保護

この API には外から呼べる入口が六つあり、そのうち二つは、いまのコードのままだと誰でも後ろの高価な資源を使い切れる。二つとは、登録の入口の後ろにある認証サービスの照会 API（従量課金で1日10,000回まで）と、タイムラインの作り直し（一回で数十分かかる）である。この資料は、入口ごとに、誰が呼べて、どれだけ呼べて、呼ばれたら何を消費するかを宣言する。読み手は、この API の入口を足す人、直す人、見直す人で、読んだ後に、どの入口に何の保護を付けるか、品質要求の資料に何を決めてもらうかを判断する。宣言に合わせてコードを直すことは、この資料とは別の作業として依頼する。

## 入口は六つで、すべて同じ待ち受け口に載っている

入口は、`AGENTS.md` が入口の組み立ての場所として示す `cmd/api/main.go` の `newMux` から列挙した。`newMux` は六つの経路を `http.ServeMux` に登録し、`main` はそれを `:8080` の一つの `http.Server` で待ち受ける（`cmd/api/main.go:23`、`cmd/api/main.go:35-42`）。取りこぼしが無いかは、リポジトリ全体を `Handle(`、`HandleFunc`、`ListenAndServe`、`http.Server`、`Listen`、`cron`、`queue`、`Subscribe`、`ticker` で検索して確かめた。ほかの待ち受け口、キューの受信口、スケジューラは見当たらない。リポジトリには配備の設定（ロードバランサ、ネットワークの境界）も無いので、六つはどれも同じように外から届くものとして扱う。

## 入口ごとの宣言

次の表は、宣言した保護を入口ごとに並べたものである。「利用上限」の列の値は `docs/品質要求.md` から写し、値が無いものは「未決」とした。表の後の節で、入口ごとの理由と、いまのコードとの差を書く。

| 入口 | 認証 | 認可 | 利用上限 | 偽装要求への対策 | 呼び出す高価な下流の資源 |
| --- | --- | --- | --- | --- | --- |
| `POST /accounts` | 利用者のトークン | 確かめた主体が自分を登録する | 認証の主体ごとに10回/分 | 不要 | 認証サービスの照会 API |
| `POST /follows` | 利用者のトークン | 登録済みの利用者が自分のフォローを足す | 利用者ごと、フォロー解除と合わせて20回/分、100回/日 | 不要 | フォローの書き込み |
| `DELETE /follows/{followee}` | 利用者のトークン | 登録済みの利用者が自分のフォローを外す | 利用者ごと、フォローと合わせて20回/分、100回/日 | 不要 | フォローの書き込み |
| `GET /timeline` | 利用者のトークン | 登録済みの利用者が自分のホームタイムラインを読む | 利用者ごと、60回/分 | 不要 | ホームタイムラインの読み取り |
| `POST /internal/timelines/rebuild` | 運用者の資格情報 | 運用者だけ | 同時に一つ（回数の値は未決） | 不要 | 全利用者のホームタイムラインの作り直し |
| `GET /healthz` | なし（適用除外） | なし | なし（適用除外） | 不要 | なし |

表で見るべきところは、利用上限の列に未決が四つあることと、認証の列が利用者のトークン以外の手段を三つ使い分けていることである。未決の値はこの資料では埋めず、最後の「未決」の節で品質要求の資料へ返す。

## 偽装要求への対策は、どの入口にも要らない

利用者は外部の認証サービスが発行したトークンを `Authorization: Bearer` の header で送り、Cookie は使わない（`AGENTS.md`）。ブラウザは、別のサイトから送られる要求にこの header を自動で付けないので、利用者のブラウザを踏み台にして状態を変える要求を送らせる攻撃は成り立たない。作り直しの入口もブラウザの Cookie に頼らないので、同じ理由で要らない。将来 Cookie で認証する入口を足すなら、状態を変える入口ごとにこの宣言を見直す。

## 利用者ごとの上限は、利用者を解決した後で数える

フォロー、フォロー解除、ホームタイムラインの三つは、登録済みの利用者の識別子ごとに回数を数える。品質要求は「利用者一人あたり」の上限を求めているからである（`docs/品質要求.md` の「負荷からの保護」）。フォローとフォロー解除は同じ枠で数え、20回/分と100回/日の両方を守る。上限を超えた要求には、時間を置いてもらう応答（いまのコードでは 429）を返す。

いまのコードは、この宣言と三点で違う。一つ目に、`limiter.PerUser` が `account.ResolveUser` の外側に巻かれている（`cmd/api/main.go:37-39`）。数える時点では利用者がまだ解決されておらず、`account.UserFrom` は空の識別子を返すので（`internal/ratelimit/ratelimit.go:24`）、全利用者が一つの枠を分け合う。結果として、フォローは API 全体で20回/分、タイムラインは全体で60回/分になり、利用者一人あたりの上限になっていない。二つ目に、100回/日の上限が見当たらない。`Limiter` は直近1分しか数えない（`internal/ratelimit/ratelimit.go:12`）。三つ目に、`ResolveUser` は「登録していなければ拒む」と書かれているが、主体の前に `u-` を付けるだけで登録を確かめていない（`internal/account/account.go:34-43`）。登録していない主体も、上の三つの入口を使える。

## 登録の入口は、認証の主体で数えないと照会 API を使い切られる

`POST /accounts` は、利用者の登録なので、内部の利用者の識別子がまだ無い。利用者の識別子で数える上限はこの入口にかからず、いまのコードにも上限は無い（`cmd/api/main.go:36`）。一方でこの入口は、主体を利用者へ解決する前に、認証サービスの照会 API を毎回呼ぶ（`internal/account/account.go:21`）。照会 API は従量課金で、契約上の上限は1日10,000回であり、超えるとその日の登録が全員止まる（`docs/品質要求.md` の「外部サービスの契約」）。正しいトークンを一つ持つ者が繰り返し呼ぶだけで、課金が増え、その日の登録が止まる。

そこで、この入口は、署名を確かめたトークンの主体（`auth.Subject`）ごとに10回/分の利用上限をかけると宣言する。主体は解決の前に得られる最小の識別子で、トークンを確かめた後なので偽れない。ただし、主体ごとの上限だけでは、認証サービスで主体を大量に作る者は止まらない。そのため、照会 API の呼び出しの回数を API 全体でも1日単位で数え、契約の10,000回より手前で止める上限も宣言する。10回/分は、登録を何度もやり直す利用者はいないので十分な値として置いた。

高価な呼び出しを主体の解決の後へ移す案は採らなかった。照会の結果（メールアドレスが確かめられているか）が登録してよいかの条件そのものなので、登録の前に呼ぶしかないからである。

## タイムラインの作り直しは、社内だと保証するものが無い

`POST /internal/timelines/rebuild` は、障害の後に運用者が手で起動し、全利用者のホームタイムラインを作り直す。一回で数十分かかる（`docs/品質要求.md` の「運用」）。経路の名前は `/internal` だが、公開の入口と同じ `:8080` の待ち受け口に載っており（`cmd/api/main.go:23`、`cmd/api/main.go:41`）、ネットワークの境界の設定も、送り手の検証も、上限も見当たらない。外から繰り返し叩けば、作り直しを何本も重ねて起こせる。この入口も**無防備**である。

この入口は、運用者だけが持つ資格情報で認証し、作り直しは同時に一つしか走らせないと宣言する。同時に一つとするのは、全利用者分を作り直す処理を重ねても結果は変わらず、負荷だけが増えるからである。運用者をどう確かめるかは、二つの案がある。一つは、公開の待ち受け口から外し、社内のネットワークからしか届かない別の待ち受け口に載せる案で、もう一つは、公開の待ち受け口のまま運用者用の資格情報を確かめる案である。この資料は、別の待ち受け口に載せたうえで運用者の資格情報も確かめる案を仮に置く。ネットワークの境界だけに頼ると、境界の設定を誤ったときに守るものが無くなるからである。どちらを採るかは未決に残す。回数の上限（1日に何回まで起動できるか）は品質要求の資料に無いので、未決として返す。

## 署名付きトークンの検証は、形式、発行者、署名、宛先、有効期間の順に固定する

利用者のトークンを受ける四つの入口は、`auth.Require` を通して `Verifier.Verify` でトークンを確かめる（`internal/auth/auth.go:16-30`）。検証は次の順に固定すると宣言する。確かめる前の値を信じて次の判断に使わないためである。

1. 形式とアルゴリズムを確かめる。アルゴリズムは、トークンが名乗るものではなく、この API が受け入れると決めた一つだけを許す。
2. 発行者が `https://auth.example.com` であることを確かめる。署名を確かめるまでは、鍵を選ぶ手がかりにだけ使う。
3. その発行者の鍵で署名を確かめる。
4. 宛先（audience）がこの API であることを確かめる。
5. 有効期間（期限切れと、まだ有効でないもの）を確かめる。時計のずれは30秒まで許す。

いまのコードは、形式を確かめた後に鍵を探し、署名、発行者、期限の順に確かめている（`internal/auth/verifier.go:31-59`）。宛先と「まだ有効でない」の確認は見当たらず、形式の確認でアルゴリズムを限っているかは、`parse` が省略されているので未確認である（`internal/auth/verifier.go:73`）。宛先を確かめないと、同じ認証サービスが別のサービス向けに発行した正しいトークンが、この API で通る。受け入れるアルゴリズム、宛先の値、30秒の幅は、どれもリポジトリにも資料にも無いので仮に置いた。30秒は、時計のずれを数十秒に抑える一般的な幅から選んだ。

未知の鍵の識別子が来たときは、鍵の一覧を取り直すが、前回の取り直しから最短の間隔が経つまでは取り直さずに拒むと宣言する。いまのコードは、未知の鍵の識別子が来るたびに間隔を置かず取り直す（`internal/auth/verifier.go:39-41`）。この取り直しはトークンを確かめる前、つまり認証の前に起きるので、利用者ごとの上限はかからない。存在しない鍵の識別子を付けたトークンを連打するだけで、誰でも認証サービスの鍵の一覧への問い合わせを無制限に起こせる。これも**無防備**な下流である。間隔の値は品質要求の資料に無いので、未決として返す。

## 適用除外は `GET /healthz` だけで、受け入れの決定が無い

`GET /healthz` は、認証も利用上限も外す。死活を確かめる仕組みは資格情報を持たずに呼ぶので、認証を付けられないからである。この入口は何も読まず書かず、204 を返すだけなので（`cmd/api/main.go:42`）、守るべき高価な下流の資源は無い。残るリスクは、大量の要求で待ち受け口そのものを混ませることだが、それはこの入口に限らない。

ただし、このリスクを受け入れた決定（ADR、リポジトリの規約の節、利用者の判断）は、リポジトリのどこにも見当たらない。そのため、この適用除外は**受け入れの決定が無い**未決として示す。

なお、登録の入口と作り直しは、いまのコードで利用上限（作り直しは認証も）を欠いているが、意図して外したことを示すものは無い。この資料はこれらを適用除外にせず、保護を付けると宣言した。

## 未決

次の項目は、この資料だけでは決められない。どれも、決める先と、決まるまでこの資料が置いた扱いを書く。

- 照会 API の呼び出しの、API 全体の1日の上限の値（契約の10,000回より手前のどこで止めるか）。品質要求の資料で決める。
- タイムラインの作り直しを1日に何回まで起動できるか。品質要求の資料で決める。
- 未知の鍵の識別子が来たときに鍵の一覧を取り直す最短の間隔。品質要求の資料で決める。
- タイムラインの作り直しを、別の待ち受け口と運用者の資格情報の両方で守るか、どちらか一方にするか。両方で守る案を仮説として置いた。
- トークンで受け入れるアルゴリズム、宛先の値、時計のずれの幅。認証サービスの設定を確かめて決める。30秒の幅は仮説として置いた。
- 各入口の認可の方針。フォローとタイムラインは「登録済みの利用者が自分の分だけを操作する」を仮説として置いた。相手にブロックされている場合や非公開の利用者を拒むかは、業務の資料に書かれていないので決めていない。
- `GET /healthz` の適用除外について、残るリスクを受け入れた決定。受け入れの決定が無い。
